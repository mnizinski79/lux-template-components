Add to Portal
1

One-time setup — start the local server

Open Terminal, navigate to the repo folder, and run this command. You only need to do this when you're adding a prototype. Once it's running, leave that Terminal window open.

# In Terminal, from the repo folder
node server.js
→

Not sure how to open Terminal or navigate to the repo? Ask Francisco to do a quick 5-minute walkthrough — it's a one-time thing.

2

Open the Add Prototype form

Go to add.html or click Add Prototype from the portal landing screen. The green banner at the top confirms the server is running and the form will write files directly.

3

Fill in the form and submit

Drop your .html file, give it a display name, pick a section (Explorations for WIP, Ready for Review for stakeholder-facing), choose your devices, add a one-line changelog note, and hit Add to Portal. The form places your file and registers it automatically.

→

Have a Figma frame for this prototype? Paste the share URL into the Figma field. A shortcut button will appear in the portal toolbar so reviewers can jump directly to the source.

4

Commit and open a PR

The form already handled the files. Just commit two files and open a pull request — once it's merged, your prototype is live in the portal.

git add _prototype/your-file.html _portal-v2/protos.js
git commit -m "Add [Prototype Name]"
git push origin proto/your-file-name
The Process

From idea to approved

Every prototype moves through four stages. The sidebar sections and status badges in the portal map directly to this flow — so everyone always knows where something stands.

1

Build Designer

Designer builds an HTML prototype and adds it to the portal under Explorations with status Draft. Multiple directions can live side by side — A, B, C variants all visible in the portal under the same subsection.

2

Internal review Design Lead

Designer shares the portal link in Slack with the design lead (Mariam / Julia). Review happens directly in the portal — the lead can view on desktop and phone, check the changelog for context, and give feedback in Slack or Figma comments. A direction is selected and the others are deprioritised (kept in Explorations, not deleted).

3

Stakeholder review Stakeholder

Designer moves the prototype to Ready for Review and updates status to In Review. A share link is sent to Allison / Chao. They view it in the portal — on desktop, on their phone via QR — and give sign-off or feedback. No Figma access needed.

4

Approved Design Lead

Once signed off, status is updated to Approved in protos.js and a changelog entry is added noting the approval. The prototype stays in the portal as a reference for engineering handoff.

Reference

Quick reference

Status values and what they mean in the portal.

Status Meaning Where it appears
Draft Work in progress — not ready for external eyes Explorations section only
In Review Polished and ready for stakeholder feedback Ready for Review section
Approved Signed off by design lead — locked for handoff Ready for Review section

File naming

Use hyphens, no spaces, no version numbers in the filename — use the changelog for version history instead.

Good: homepage-mobile.html
Avoid: Homepage Mobile v2 FINAL.html

ID prefixes

Prototype IDs in protos.js use a prefix to indicate stage.

r- for Ready for Review
x- for Explorations

Example: x-homepage-mobile
