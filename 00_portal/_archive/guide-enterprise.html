The Stack

Three services, one pipeline

GitHub is the source of truth. Vercel watches GitHub and deploys automatically. Claude is the AI assistant every designer uses — with the same project context built in because the config files live in the repo.

GitHub

Enterprise

Every prototype is a pull request. Full version history, branch protection, review approvals. Nothing gets published without a merge — which means nothing gets published by accident.

Vercel

Pro / Enterprise

Watches the GitHub repo. Every merged PR auto-deploys to the permanent URL in under 60 seconds. Every open PR gets a preview URL — so you can review before merging, not after.

Claude

Enterprise

AI assistant for building prototypes from Figma. Enterprise means every designer on the team has the same model, same capabilities. Context is unified via CLAUDE.md files that live in the repo — clone the repo, get the context.

For Designers

Adding a prototype

No terminal. No Node.js. No manual file moves. Open the portal in your browser, fill out the form, hit submit. The rest is automatic.

1

Open the Add Prototype form

Go to the portal's permanent URL and click + Add Prototype in the nav. The form lives on Vercel — no local server needed. It's always available from any browser, any machine.

2

Fill in the form

Drop your .html file, give it a display name, pick a section, set devices, and add a one-line changelog note. Here's what each field does:

FieldWhat it does
HTML fileYour prototype. Must be a single self-contained .html file. The filename is permanent — use hyphens, no spaces.
Display nameShown in the sidebar. Auto-suggested from the filename. Keep it short and human-readable.
SectionExplorations for WIP or internal review. Ready for Review for stakeholder-facing, polished work.
SubsectionGroups A/B/C directions together in the sidebar under Explorations.
StatusDraft, In Review, or Approved. Controls the badge shown next to the prototype in the sidebar.
DevicesWhich device tabs appear in the portal toolbar. Only tick what your prototype actually supports.
Figma URLOptional. Adds a button in the portal toolbar so reviewers can jump to the source Figma frame.
ChangelogOne line describing this version. Shown in the changelog drawer. Add more entries over time.
3

Hit submit — a PR opens automatically

The form talks to the GitHub API directly. It creates a branch, commits your HTML file to _prototype/ and your entry to protos.js, then opens a pull request — all in one step. You'll get a link to the PR so you can share it for review.

→

As soon as the PR opens, Vercel builds a preview URL for that branch. You can share the preview URL with the design lead before anything is merged — no waiting.

4

Design lead merges — Vercel deploys

The design lead reviews the prototype at the preview URL, approves the PR on GitHub, and merges it. Within ~60 seconds Vercel deploys the change to the permanent portal URL. The prototype is live for everyone — stakeholders, the wider team, engineering handoff.

Claude Context

Unified across the team

Every designer on the team uses Claude with the same context. That context isn't stored on anyone's machine — it lives in the repo as two CLAUDE.md files. Clone the repo, get the context. No zip downloads, no manual setup, no one working from a blank slate.

The rule: CLAUDE.md files are checked into the repo like any other file. When someone clones the repo, they get them automatically. When Francisco updates the context — new sprint info, new collaborators, revised design rules — everyone gets the update on the next pull.

Clone the repo. Open Claude Code in the project folder. That's it — Claude reads the CLAUDE.md files automatically on startup. No briefing document to track down, no setup call needed.

Context stays current

Sprint changes, new collaborators, revised scope — update the CLAUDE.md in a PR. Everyone on the team pulls the latest and Claude has the updated context on the next session. One source of truth.

The Process

From idea to approved

Every prototype moves through four stages. The sidebar sections and status badges in the portal map directly to this flow — so everyone always knows where something stands.

1

Build Designer

Designer builds an HTML prototype — with Claude's help if needed — and adds it to the portal under Explorations with status Draft. Multiple directions can live side by side as A/B/C variants under the same subsection.

2

Internal review Design Lead

Designer shares the portal link in Slack with the design lead (Mariam / Julia). Review happens in the portal — lead checks desktop and phone views, reads the changelog, gives feedback in Slack or Figma comments. A direction is selected; others stay in Explorations, not deleted.

3

Stakeholder review Stakeholder

Designer moves the prototype to Ready for Review, updates status to In Review, and sends a share link to Allison / Chao. They open it in the portal — on desktop, on their phone via QR — and give sign-off or feedback. No Figma access needed.

4

Approved Design Lead

Once signed off, status is updated to Approved in protos.js and a changelog entry is added noting the approval. The prototype stays in the portal as a living reference for engineering handoff.

File naming

Use hyphens, no spaces, no version numbers in the filename — use the changelog for version history instead.

Good: homepage-mobile.html
Avoid: Homepage Mobile v2 FINAL.html

ID prefixes

Prototype IDs in protos.js use a prefix to indicate stage.

r- for Ready for Review
x- for Explorations

Example: x-homepage-mobile
